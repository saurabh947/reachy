# Gemini Can Drive the Arm, Not the Robot

No: as of 15 October 2026, no Gemini Robotics model can be the single brain for a talking robot built from a Reachy Mini Lite and an SO-101. Even the whole family together needs your own code at both ends. The VLAs (Gemini Robotics 2 and On-Device 2) turn images and text into motor actions. They do not hear, speak or call tools, and both sit behind a trusted-tester waitlist with no public API and no price. The one model anyone can call, Gemini Robotics-ER 2, hears, sees, plans and calls any function, including your emotion SDK. But it returns only text, so it needs a separate text-to-speech (TTS) service to talk. On the hardware side, SO-101 is one of only four bodies On-Device 2 is built to adapt to, and DeepMind reports SO-101 task success rising from 6.7% to 53.3% as more data is added. But the model is served from an NVIDIA Docker image, not a Mac, and no Gemini model controls a head, neck or gaze, so Reachy's head stays under your SDK code either way. Your current stack is Gemini 3.8 Live for voice and tools, ER 2 as a spatial tool, and the local emotion model as a tool. It already follows Google's split between an orchestrator (the planning model) and an executor (whatever moves the motors), and it has a better voice than Google's own sample. Keep it and add one swappable arm executor behind a fixed tool: taught poses now, SmolVLA on the Mac next, On-Device 2 if Google accepts you. For long-running tools, decide by who is waiting for the result:
- Keep the slow room search NON_BLOCKING, with an explicit WHEN_IDLE result and strict prompt and description rules (option a).
- Declare instant question tools such as `detect_emotion` BLOCKING.
- Put real blocking in whichever layer plans the physical steps.

If ER 2 streaming ever becomes the brain, the choice disappears, because it supports only blocking calls for robotics.

## Only ER 2 is public, and no Gemini Robotics model speaks

Google's 30 July 2026 launch defined the current family as three models: the Gemini Robotics 2 VLA, Gemini Robotics ER 2, and Gemini Robotics On-Device 2 ([DeepMind blog](https://deepmind.google/blog/gemini-robotics-2-brings-whole-body-intelligence-to-robots/)). **Only ER 2 can be called without approval.** It is in public preview as `gemini-robotics-er-2-preview`, with a Live API variant, `gemini-robotics-er-2-streaming-preview` ([Gemini API model page](https://ai.google.dev/gemini-api/docs/models/gemini-robotics-er-2-preview)). The VLA is listed as "Private preview" and On-Device 2 as "Trusted testers", both reached through a waitlist ([DeepMind VLA page](https://deepmind.google/models/gemini-robotics/vla/); [DeepMind On-Device page](https://deepmind.google/models/gemini-robotics/on-device/)). Every Gemini VLA generation since March 2025 has been gated the same way. The waitlist form accepts individuals ticking "personal interest", but joining it is not acceptance ([Trusted Tester form](https://docs.google.com/forms/d/1sM5GqcVMWv-KmKY3TOMpVtQ-lDFeAftQ-d9xQn92jCE/viewform)). DeepMind says it is working with "100+ trusted testers" ([DeepMind Gemini Robotics](https://deepmind.google/models/gemini-robotics/)), and neither VLA has a published price ([TechTimes](https://www.techtimes.com/articles/322309/20260730/gemini-robotics-2-controls-full-humanoids-legs-torso-arms-fingers-under-one-policy.htm)).

|---|---|---|---|---|---|

| On-Device 2 (VLA) | Trusted testers | Text, image, proprioception | Numeric robot actions | None | Local Docker image, NVIDIA GPU |

Sources: [ER 2 model page](https://ai.google.dev/gemini-api/docs/models/gemini-robotics-er-2-preview), [Robotics streaming guide](https://ai.google.dev/gemini-api/docs/robotics-streaming), [On-Device 2 model card](https://deepmind.google/models/model-cards/gemini-robotics-on-device-2/), [3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live), [gemini-robotics-sdk flywheel CLI](https://github.com/google-deepmind/gemini-robotics-sdk/blob/main/safari_sdk/flywheel/flywheel_cli.py).

The table rules out the design as literally stated. A VLA has no audio channel and no function calling, so it cannot hold a conversation or decide to call `detect_emotion`. In Google's own design, the talking and tool calling happen in ER, which "observes the room, reasons about the steps needed, directs the VLA to carry out actions, and tracks progress" ([DeepMind blog](https://deepmind.google/blog/gemini-robotics-2-brings-whole-body-intelligence-to-robots/)). In Google's code, the VLA appears as a tool named `run_instruction(instruction=...)` that ER calls ([robotics-samples ER 2 script](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/scripts/er2_developer_api_example.py)). Your emotion SDK fits that pattern without changes. Google's own Live robotics sample declares a non-robot `get_calendar` tool next to `pick` and `navigate` ([robotics-samples tools.py](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/tool/tools.py)).

Voice is the problem. Google's streaming guide says plainly that "Gemini Robotics ER 2 returns text": the application sends finished replies to a separate TTS provider, or declares TTS as a tool ([Robotics streaming guide](https://ai.google.dev/gemini-api/docs/robotics-streaming)). Your own `scene_brain.py` already records ER 2 streaming rejecting audio output. Emotion follows the same logic. Gemini 3.8 Live removed affective dialogue from the API ([3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)), and ER 2 has no affective features, so **your local emotion model is the only emotion path in every design considered here.**

Two practical facts follow for ER 2. First, ER preview models are short-lived. ER 1.5 shut down on 30 April 2026 after about seven months, and ER 1.6 on 31 August 2026 after about four and a half ([Gemini API deprecations](https://ai.google.dev/gemini-api/docs/deprecations)), so keep `GEMINI_ER_MODEL` configurable, as the app already does. Second, ER 2's $1.00 input / $5.00 output per million tokens is a promotional rate that **doubles to $2.00 / $10.00 on 1 January 2027** ([Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing)).

## SO-101 is one of four On-Device 2 bodies; Reachy's head is none

The arm is the hopeful half. DeepMind's launch post names SO101 among the On-Device 2 platforms ([DeepMind blog](https://deepmind.google/blog/gemini-robotics-2-brings-whole-body-intelligence-to-robots/)). The public SDK's On-Device 2 training recipe requires an `--embodiment` flag whose only allowed values are **`trossen`, `so101`, `dexmate` and `fr3_duo`** ([flywheel_cli.py](https://github.com/google-deepmind/gemini-robotics-sdk/blob/main/safari_sdk/flywheel/flywheel_cli.py)). The On-Device 2 model card reports SO-101 success rising from **6.7% to 53.3%** as hours of data per task increase, against 0% to 6.7% for On-Device 1. It does not name the tasks or the number of demonstrations ([On-Device 2 model card](https://deepmind.google/models/model-cards/gemini-robotics-on-device-2/)). Google says the model adapts to new bi-arm bodies "in a few hours, typically with fewer than 200 examples" ([DeepMind blog](https://deepmind.google/blog/gemini-robotics-2-brings-whole-body-intelligence-to-robots/)). Expect something closer to a coin flip than a reliable product.

Fine-tuning is a closed-weight managed service. You never hold the weights. You upload episodes with `flywheel-cli upload_data`, train on Google's servers with `flywheel-cli train`, then download a checkpoint and a Docker inference image ([gemini-robotics-sdk](https://github.com/google-deepmind/gemini-robotics-sdk)). The SDK ships a **LeRobot-to-MCAP converter** that requires `lerobot >= 0.4.0` ([conversion script](https://github.com/google-deepmind/gemini-robotics-sdk/blob/main/examples/logging/lerobot_data_conversion_script.py)), so demos you record today in LeRobot can be reused later. The serving side is the obstacle. `flywheel-cli serve` runs the image with `--gpus device=0` (with a slower `--use_cpu` fallback) ([flywheel_cli.py](https://github.com/google-deepmind/gemini-robotics-sdk/blob/main/safari_sdk/flywheel/flywheel_cli.py)). The `safari-sdk` wheels are built only for Linux x86_64 ([PyPI safari-sdk](https://pypi.org/project/safari-sdk/)). **Your M3 Pro is not a supported host.** Acceptance would mean adding a Linux NVIDIA box on the LAN, or using cloud serving if Google offers it. The only latency figures Google has published are for the 2025 Gemini Robotics 1.0: under 160 ms for the cloud backbone, about 250 ms end to end, and an effective 50 Hz through chunked actions ([arXiv 2503.20020](https://arxiv.org/html/2503.20020)).

The sources do not say whether `so101` means one arm or a bimanual pair. Google frames On-Device 2 adaptation around "bi-arm" robots, so **your planned second arm moves you toward Google's sweet spot, not away from it.**

The head is a dead end for Gemini. No Gemini Robotics source describes a head, neck, gaze or camera-pose action. Franka Duo's head cameras in the SDK examples are observations only ([SDK policy example](https://github.com/google-deepmind/gemini-robotics-sdk/blob/main/examples/model/gemini_robotics_policy_example.py)). So are the Unitree G1's head cameras in the CLIFT fine-tune, whose actions cover arms, hands and base but not the neck ([CLIFT, arXiv 2607.29172](https://arxiv.org/html/2607.29172)). The fixed embodiment list gives no public way to add a Stewart-platform head.

Open models do not rescue "one VLA drives both" either, at least not yet. LeRobot has no `reachy_mini` robot type, and the community PR adding one has waited for review since December 2025 ([LeRobot PR #2726](https://github.com/huggingface/lerobot/pull/2726)). Builders who pair heads with arms freeze the head while a policy runs. XLeRobot's guide says to "keep consistent head servos angles" during both recording and inference ([XLeRobot VLA docs](https://xlerobot.readthedocs.io/en/latest/software/getting_started/VLA_ACT.html)). Treating the head as an action is a 2026 research topic on large backbones and custom rigs, for example ActiveScale on π0.5 and Vision in Action ([ActiveScale](https://arxiv.org/html/2609.18514); [Vision in Action](https://arxiv.org/abs/2506.15666)). It has not reached hobby-scale models.

The most Gemini-native robot you could actually build has four parts:
- 3.8 Live for voice.
- ER 2 as the planner.
- On-Device 2 on an NVIDIA box for the SO-101, if you are accepted.
- Your own code for the head, emotion and glue.

Google's newest robotics release points the same way. On 13 October 2026, Gemini 4 Argon for Robotics did SO-101 pick-and-place by **writing and debugging planner code** from logs and wrist-camera video, cutting task time from 58.9 s to 17.4 s. No VLA was involved ([Google Developers Blog](https://developers.googleblog.com/gemini-4-argon-for-robotics/)). For small arms, Google's public path is a reasoning model plus code, not a public VLA.

## Your Live-plus-ER stack already mirrors Google's layering

Google publishes two approved shapes. In the first, **one Live session is the whole brain**: either a native-audio model with tools, or ER 2 streaming with TTS declared as a tool. Google's sample ships both behind a `--model` flag ([robotics-samples live-api](https://github.com/google-gemini/robotics-samples/tree/main/live-api)). In the second, **ER orchestrates and a VLA executes**. That is the Gemini Robotics 1.5 "agentic framework" carried into ER 2 ([DeepMind GR 1.5 blog](https://deepmind.google/discover/blog/gemini-robotics-15-brings-ai-agents-into-the-physical-world/)). No official sample chains a Live audio model to ER and then to a VLA. Your app is a third shape: a voice front end that hands spatial reasoning to ER. It is coherent but unofficial. The Reachy community also builds this way. Pollen's conversation app pairs a realtime voice model with tool calls and a 60 Hz movement manager ([Google DEV walkthrough](https://dev.to/googleai/build-a-talking-robot-with-gemini-live-and-reachy-mini-20e2)). The one public ER 2 Reachy app instead runs ER 2 streaming as the brain and speaks through Gemini TTS ([max-lm/reachy_mini_er2](https://huggingface.co/spaces/max-lm/reachy_mini_er2/raw/main/README.md)).

| | Current: Live → ER tool → your executors | ER 2 streaming as the one brain | Gemini end state: Live → ER 2 → On-Device 2 |
|---|---|---|---|
| Voice | Native audio, server turn-taking, barge-in, proactive audio | Text to external TTS; app handles barge-in | Same as current |
| Spatial reasoning | On demand per call (plan ~5 s, room search 10–15 s) | Continuous; ER sees every frame at ≤1 fps | On demand, plus ER's own multi-step tool loop |
| Tool semantics | NON_BLOCKING with SILENT / WHEN_IDLE / INTERRUPT | Blocking only for robotics; no scheduling | Async at Live layer, blocking inside ER loop |
| Contexts | Two: Live session plus stateless ER calls | One shared context | Two or three, explicit handoff |
| Token price per 1M | Live audio $3 in / $12 out; ER $1 / $5 (2026) | $1 in / $5 out (2026), plus TTS and ~1 Hz heartbeat turns | Current plus ER loop plus a GPU host |
| Arm | Taught poses via per-arm queue | Same, as blocking tools | On-Device 2 if accepted |
| Head and emotion | Your SDK code; local model as tool | Same | Same |
| Usable today | Yes | Yes | No |

Prices from [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing); semantics from [Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities) and the [Robotics streaming guide](https://ai.google.dev/gemini-api/docs/robotics-streaming).

The strongest case for making ER 2 streaming the brain:
- One context, so the planner knows what was said.
- ER watches every frame.
- It can "trigger safety tool calls and bring the robot to a stop when a person gets too close" ([DeepMind blog](https://deepmind.google/blog/gemini-robotics-2-brings-whole-body-intelligence-to-robots/)).
- Its input tokens cost a third of Live audio's.

The token saving is smaller than it looks. ER streaming does not reason over video alone. Google says "video frames alone do not trigger a new reasoning turn" and prescribes a text "heartbeat" at about 1 Hz ([Robotics streaming guide](https://ai.google.dev/gemini-api/docs/robotics-streaming)). Live sessions re-bill every token in context on every turn ([Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)). A heartbeat-driven brain can therefore cost more than a Live session that calls ER only on demand. It also gives up native prosody, proactive audio and server-managed turn-taking, which are the qualities that matter most for an emotion-aware social robot. Choose it only if continuous spatial autonomy ever matters more to you than conversation.

The current stack's real weakness is the other direction: ER sees none of the conversation. Fix it by passing a short task summary with each ER call, or by keeping a long-lived ER Interactions thread linked with `previous_interaction_id` ([Task orchestration guide](https://ai.google.dev/gemini-api/docs/robotics-orchestration)).

Both shapes share the Live session's operating costs. Audio accumulates at about 25 tokens per second. Proactive audio is permanently on in 3.8, so input is billed "the entire time the Live API is listening" ([Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)). Audio-plus-video sessions are capped at 2 minutes without context compression, and connections last about 10 minutes, with resumption tokens valid for 2 hours ([Live session management](https://ai.google.dev/gemini-api/docs/live-session)). An always-on robot therefore needs context compression and session resumption whatever brain it uses.

## Build a swappable arm executor, not a single brain

The recommended architecture keeps three layers and makes the bottom one replaceable.

**Layer 1: Gemini 3.8 Live** stays the persona and voice. Its tools are `detect_emotion`, `look_at_scene`, `plan_task`, `move_arm`, `stop`, and one new tool, `run_arm_skill(skill)`.

**Layer 2: standard ER 2**, called through the Interactions API. It handles pointing and planning. For a multi-step task, it runs its own function-calling loop over arm skills. Google's orchestration example declares `move` and `setGripperState`, caps the loop at 15 steps and uses low thinking ([Task orchestration guide](https://ai.google.dev/gemini-api/docs/robotics-orchestration)).

**Layer 3: the executors.**
- The head runs on the Reachy SDK: `look_at_image` for gaze and the Pollen emotions library for expression. That library needs `reachy_mini` v1.8.4 or later, and the current release is v1.12.0 ([emotions library](https://huggingface.co/datasets/pollen-robotics/reachy-mini-emotions-library); [reachy_mini releases](https://github.com/pollen-robotics/reachy_mini/releases)). Upgrade if you are still on v1.6.
- An arbiter parks the head at a fixed work pose while an arm policy runs, and blocks expressive head moves until the policy finishes. This keeps the camera view stable, which policies depend on.
- If emotion also drives a reactive motion layer, debounce it the way the community emotion-mirror app does: confidence ≥0.45, two agreeing checks, and a 3 s cooldown ([emotion-mirror](https://huggingface.co/spaces/NathanSegers/reachy-mini-emotion-mirror/raw/main/README.md)).

The `run_arm_skill` seam is the core of the plan. Behind it you can swap executors without touching Layer 1. This is the pattern XLeRobot's RoboCrew uses: a Gemini agent calls arm-skill tools backed by a LeRobot policy server, and a separate look-around tool moves the head ([XLeRobot LLM agent docs](https://xlerobot.readthedocs.io/en/latest/software/getting_started/LLM_agent.html)). Physical Intelligence's Hi Robot shows why the hierarchy pays off. A planner that issues language commands to π0 reached **76% instruction accuracy, against 30% for a GPT-4o planner and 36% for a flat VLA** ([Hi Robot](https://www.pi.website/research/hirobot)). The skill tool should map an enum to a task string identical to the one used in recording, since fine-tuned VLAs follow the training phrasing. It should also detect success with a time budget plus an ER check. Policies do not report "done", and ER 2's own progress estimate scores only 57.4% across five progress bands ([Google ER 2 blog](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)).

| Stage | Executor behind `run_arm_skill` | Runs on | What to expect |
|---|---|---|---|
| 0 (now) | Taught poses through the per-arm queue | Mac | Deterministic gestures only |
| 1 | SmolVLA, 50–100 demos per skill, head parked as front camera plus wrist camera | Mac via PyTorch MPS | 90% in-distribution / 50% out-of-distribution on SO-101 Lego pick ([SmolVLA paper](https://arxiv.org/html/2506.01844)); 32.5% average on a harder four-task benchmark ([arXiv 2606.08881](https://arxiv.org/html/2606.08881)) |
| 1b (optional) | π0.5 on a rented CUDA GPU as a LeRobot policy server | Cloud GPU, Mac as robot client | 56.25% on the same benchmark, the best measured |
| 2 (if accepted) | On-Device 2, trained on the same LeRobot data converted to MCAP | Linux x86_64 NVIDIA box | 53.3% on SO-101 tasks per DeepMind |
| 3 | Bimanual: LeRobot `bi_so_follower` with SmolVLA, X-VLA or On-Device 2 | As above | X-VLA ships an `so101_bimanual` action mode ([X-VLA docs](https://huggingface.co/docs/lerobot/en/xvla)) |

SmolVLA is the right first executor because it is the only VLA with replicated SO-101 results that also runs on your laptop. LeRobot recommends about 50 episodes and warns that 25 "was not enough" ([LeRobot SmolVLA docs](https://huggingface.co/docs/lerobot/en/smolvla)). Training takes about 4 hours on one A100 for 20,000 steps. SmolVLA needs about 2 GB at inference, against 14 GB for π0 ([LeRobot async docs](https://huggingface.co/docs/lerobot/en/async)). A 50-action chunk measured **about 205 ms with PyTorch MPS on an M5 Pro** ([mlx-smolvla](https://pypi.org/project/mlx-smolvla/)). Expect slower on your M3 Pro, but chunked asynchronous execution hides most of that.

The same benchmark also shows SmolVLA's weak spot: it recovers after an error only 3.2% of the time, against 30.8% for π0.5 ([arXiv 2606.08881](https://arxiv.org/html/2606.08881)). Plan to retry in Layer 2 rather than inside the policy.

If Gemini never opens up, the alternatives sit behind the same seam:
- **π0.5** through openpi, which supports only Ubuntu and needs a GPU with more than 8 GB ([openpi](https://github.com/Physical-Intelligence/openpi)).
- **GR00T N1.7**, which needs a 16 GB+ GPU for inference and 40 GB+ for fine-tuning, under NVIDIA's model licence ([Isaac-GR00T](https://github.com/NVIDIA/Isaac-GR00T)).
- **MolmoAct2**, whose zero-shot SO-100/101 checkpoint is the only one built specifically for these arms. It needs an NVIDIA GPU and a joint-frame correction ([LeRobot MolmoAct2 docs](https://huggingface.co/docs/lerobot/en/molmoact2)).
- **Physical Intelligence's hosted Pi API beta**, launched 13 October 2026 with data upload, fine-tuning and cloud inference ([Physical Intelligence](https://www.pi.website/)). It is the closest non-Google analogue to Google's managed On-Device service.

Apply to the trusted-tester program now, naming SO-101 and On-Device 2. The application costs nothing, and recording in LeRobot keeps your data portable either way.

## Block where a planner waits, not where a listener waits

On `gemini-3.8-live`, asynchronous calls (`NON_BLOCKING`) are the default, `BLOCKING` remains available, and the `scheduling` field you put in each `FunctionResponse` controls delivery ([3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)):
- `INTERRUPT` speaks the result immediately.
- `WHEN_IDLE` waits until the current utterance ends.
- `SILENT` adds the result to context without speaking ([Live API tool use](https://ai.google.dev/gemini-api/docs/live-tools)).

With BLOCKING, 3.8 Live "waits for tool execution before speaking" ([Live API thinking guide](https://ai.google.dev/gemini-api/docs/live-api/thinking)). That means **10–15 s of dead air** during a room search. If voice activity detection hears speech or noise during that time, the server "discards any pending function calls" and reports the cancelled IDs ([Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)).

Two documentation conflicts matter here. First, the tool-use guide still says calls are sequential "by default", while the 3.8 model page says NON_BLOCKING is the default ([Live API tool use](https://ai.google.dev/gemini-api/docs/live-tools)). Second, the pages disagree on the spelling `INTERRUPT` versus `INTERRUPTED`. Your `live_conversation.py` declares no `behavior` on any tool, and it sends the `look_at_scene` result with no `scheduling` field, so the app currently depends on whichever default the server applies.

The wrong guess you saw is the known failure mode of asynchronous tools. Gemini keeps talking while the search runs. It also sees its own camera feed at up to 1 fps, so it can "eyeball" an answer before ER returns one. Google documents no guardrail against this beyond prompting. Its best-practices page says to tell Gemini "under what conditions a tool call should be invoked" ([Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)).

**Option (a) is the right call for slow question tools, but only with hardening beyond a prompt rule:**
- Declare `behavior: NON_BLOCKING` explicitly on every tool.
- Return the search result with explicit `WHEN_IDLE`.
- Say in the tool description that the result arrives later as a separate message, and that until it arrives the model does not know the answer.
- Keep the system-prompt rule: say you are looking, never state a location before the result arrives, and say you are still looking if asked.
- Shorten the window in which a guess can happen. The room search makes up to six sequential ER pointing calls, one per heading, and `scene_brain.py` sets no thinking level. Google's Live robotics sample runs ER 2 at `thinking_level="low"` ([robotics-samples session_config](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/session_config.py)), and pointing is the task Google says needs the least thinking. Checking the current frame first and stopping at the first hit should cut the typical case further.

**Option (b), BLOCKING, has a real case: it makes a premature answer structurally impossible.** Google's sample also marks queries such as `get_calendar` and `get_battery` as BLOCKING ([robotics-samples tools.py](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/tool/tools.py)). That precedent is weaker than it looks, though. The sample defaults to `gemini-3.1-flash-live-preview`, which supports only synchronous calls ([Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)). For a 15 s search, (b) trades a prompt-compliance risk for two guaranteed costs: dead air, and fragility to any noise. Your receive loop also has no handler yet for cancelled-call IDs. **Use (b) for instant question tools.** `detect_emotion` is answered inline and is usually instant, so blocking it costs nothing and removes any chance Gemini guesses the user's mood.

There is a third option. Google's own recommendation for tools that "take several seconds to run" is `gemini-3.8-live-extended-thinking`, which speaks conversational fillers automatically ([Live API thinking guide](https://ai.google.dev/gemini-api/docs/live-api/thinking)). It supports only NON_BLOCKING calls and **no function scheduling**. Switching would drop the SILENT path your `move_arm` design depends on.

| Tool class | Example | Today on 3.8 Live | If ER 2 streaming becomes the brain | With a VLA executor |
|---|---|---|---|---|
| Instant question | `detect_emotion` | BLOCKING | BLOCKING (only option) | Unchanged |
| Slow question | Room search, `plan_task` | NON_BLOCKING, WHEN_IDLE result, hard rules | BLOCKING after a spoken "let me look"; search becomes ER-driven head turns | Unchanged at Live; ER runs search inside its loop |
| Unprompted gesture | Wave, gripper flick | NON_BLOCKING; SILENT on success, WHEN_IDLE on failure | BLOCKING, no scheduling | Unchanged |
| Requested task | "Pick up the cup" | Not yet possible | BLOCKING `run_instruction` | Live: NON_BLOCKING, WHEN_IDLE for **both** outcomes; ER loop blocks |
| Safety | `stop`, motor fault | Stop preempts queue; mid-move fault WHEN_IDLE; idle fault injected with `turn_complete=True`, which interrupts | BLOCKING stop; ER can trigger safety calls | Every fault INTERRUPT, since an arm under a policy is rarely idle |

If ER 2 streaming becomes the brain, the choice disappears. Google states that "only blocking function calls are supported when using the Live API for robotics" ([Robotics streaming guide](https://ai.google.dev/gemini-api/docs/robotics-streaming)). The silence problem then moves. Speech is itself a tool in that design: Google's sample runs TTS as a NON_BLOCKING background task. So ER says "let me look" through TTS before it blocks. The sample also pauses the heartbeat while any blocking tool runs and sends a fresh frame before returning the result ([robotics-samples tool_call_handler](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/core/tool_call_handler.py)). The room search also changes shape. Because ER sees frames directly, a single opaque 15 s tool becomes a sequence of short blocking head turns with ER looking between them. The "question" tool dissolves into the planner's own loop.

A VLA executor changes the arm's semantics. Arm actions become long: RoboCrew's example budgets 45 s per skill ([XLeRobot LLM agent docs](https://xlerobot.readthedocs.io/en/latest/software/getting_started/LLM_agent.html)), and On-Device policies emit 1.6 s chunks and replan ([CLIFT](https://arxiv.org/html/2607.29172)). They also become uncertain, at 33–56% success on the SO-101 benchmark. That has three consequences. First, a task the user asked for is a question tool in disguise, because the user is waiting for the outcome. Its success should come back WHEN_IDLE, not SILENT. Keep SILENT for unprompted gestures. Second, the prompt rule extends from facts to deeds: never claim an action succeeded before its result arrives. Third, real blocking belongs in ER's Interactions loop, which waits for each `function_result` by design. That satisfies Google's "physical actions must use BLOCKING" guidance without muting Reachy. Your per-arm queue still guarantees ordering. `stop` must stay non-blocking and preempt the queue, because a server-side cancellation drops only the call ID; nothing stops the motors unless the app does.

## Conclusion

A "vertically integrated" Gemini brain is the wrong goal. Even Google ships its robot brains as layers with tools between them, and its only public example of a small-arm success this month came from a reasoning model writing code. The lasting assets in this project are the seams: `run_arm_skill` with a fixed skill vocabulary, a head arbiter, and a per-tool rule for who waits on each result. Each layer behind them is likely to be replaced within a year. ER previews have lasted 4–7 months, ER 2's price doubles in January, and Argon arrived two days ago. Treating "BLOCKING vs NON_BLOCKING" as "planner waits vs listener waits" also generalises. It turns today's room-search bug into a design rule that still holds when the arm gains a learned policy.

The verdict would flip on three events. The first is trusted-tester acceptance together with a Linux GPU box, which makes On-Device 2 a drop-in executor, especially once the second arm turns the SO-101 into the bi-arm body Google targets. The second is Google publishing a Live-to-ER-to-VLA reference, which would make your third shape official. The third is any Gemini model gaining head or gaze actions. Until one of these happens, the hardest unsolved problem is not which model is the brain. It is making a robot that is right only about half the time on manipulation say so honestly, out loud, at the right moment.
