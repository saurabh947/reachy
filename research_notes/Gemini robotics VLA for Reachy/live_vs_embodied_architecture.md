# Gemini 3.8 Live vs Gemini Robotics (ER 2, Gemini Robotics 2 VLA, On-Device 2): capabilities, layered architecture, and tool blocking for a talking robot that acts

State as of 2026-10-15 (research date). Every finding carries the source's own date: a "last updated" stamp for ai.google.dev pages, a publication date for blogs and model cards, a commit date for GitHub. All ai.google.dev pages were read on 2026-10-15. Raw page text was fetched and grepped, so the quotes below are verbatim unless marked otherwise.

## 1. Can any Gemini Robotics model (ER 2, the VLA, On-Device) hold a realtime voice conversation or take audio input, or is the Live API still required for voice?

### Takeaway
No Gemini Robotics model **speaks**. ER 2 (both endpoints) and the VLAs output text or actions only. ER 2 does **take audio input**, and its separate `gemini-robotics-er-2-streaming-preview` endpoint runs **on the Live API** (WebSocket, 16 kHz PCM in, text out). So ER 2 streaming can *listen* in real time, but Google's own pattern for speech output is an external TTS that ER calls as a tool. Native speech-to-speech with barge-in, proactive audio and Google-managed voices still requires a Live audio model (`gemini-3.8-live` or `gemini-3.8-live-extended-thinking`). The VLAs (Gemini Robotics 2, On-Device 2) take text instructions plus images plus proprioception and output robot actions. They have no audio in or out, and access to them is restricted.

### Cited Findings
**Gemini 3.8 Live (the voice layer)**
- `gemini-3.8-live` is a stable model. Inputs are "Text, images, audio, video"; output is "Text and audio"; limits are 131,072 input and 65,536 output tokens. It is described as "the default option for most low-latency voice agent experiences and real-time dialogue without reasoning-induced delays", and it "supports interleaved reasoning, asynchronous function calling, full session client content updates, and built-in audio streaming." Not supported: code execution, structured outputs, caching, Maps grounding, URL context, Batch. (Updated 2026-09-15.) — [Gemini 3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)
- The 3.8 Live migration notes: "Proactive audio is now permanently enabled. Setting `proactive_audio: false` returns an error." "Affective dialogue is removed from the API." "Audio is the supported output"; enable output transcription to get text. Turn coverage defaults to `TURN_INCLUDES_AUDIO_ACTIVITY_AND_ALL_VIDEO`. (2026-09-15) — [Gemini 3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)
- There is a second 3.8 voice model, `gemini-3.8-live-extended-thinking`, which "adds background reasoning to real-time voice sessions. The model plans and calls asynchronous tools in the background while speaking natural conversational fillers." (2026-09-15) — [Live API Thinking guide](https://ai.google.dev/gemini-api/docs/live-api/thinking)
- In the Live API, video frames are sent "as individual images (e.g., JPEG or PNG) at a specific frame rate (max 1 frame per second)." (2026-09-18) — [Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)

**Gemini Robotics-ER 2 (the reasoning or orchestration layer)**
- `gemini-robotics-er-2-preview`: inputs "Text, images, video, audio", output "Text"; "Audio generation: Not supported"; "Live API: Not supported." `gemini-robotics-er-2-streaming-preview`: same inputs, output "Text", "Live API: Supported", function calling and thinking supported, but **no** code execution, caching, structured outputs, computer use, Maps grounding, URL context or Batch. Both were last updated "July 2026". (Page updated 2026-10-08.) — [ER 2 model page](https://ai.google.dev/gemini-api/docs/models/gemini-robotics-er-2-preview)
- The standard ER 2 "Builds on Gemini 3.5 Flash". The streaming endpoint is "Optimized for real-time streaming using the Live API. Use this model for low-latency robot agents that process continuous audio and video input." ER 1.6 "was deprecated on August 31, 2026." (2026-10-06) — [Robotics overview](https://ai.google.dev/gemini-api/docs/robotics-overview)
- The ER 2 streaming specification gives input as "Audio (raw 16-bit PCM audio, 16kHz, little-endian), images (JPEG <= 1FPS), text", output as "Text", and the protocol as "Stateful WebSocket connection (WSS)". (2026-09-11) — [Robotics with streaming](https://ai.google.dev/gemini-api/docs/robotics-streaming)
- On speech output, Google's guidance is verbatim: "Gemini Robotics ER 2 returns text. Your application routes completed responses to a separate TTS provider (such as Gemini TTS) via an injected callback… You can also declare TTS as a tool so the model treats 'say something' the same as 'move the arm.'" The example tool is `send_message(target, message)`. (2026-09-11) — [Robotics with streaming](https://ai.google.dev/gemini-api/docs/robotics-streaming)
- The ER 2 model card (published 2026-07-30) lists inputs "Text, image, video, and audio" (interleaved, up to 128k context) and output text only (up to 64K). It is based on Gemini 3.5 Flash. — [ER 2 model card](https://deepmind.google/models/model-cards/gemini-robotics-er-2/)
- The ER 2 launch post (2026-07-30) says ER 2 is a "high-level brain for robots" that handles conversation, and that robots can "chat with humans" with audio streamed in. It does not claim spoken output. — [Google blog: Introducing Gemini Robotics ER 2](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)

**VLAs (executor layer)**
- The Gemini Robotics 2 VLA "converts vision and language input into motor control". It "understands and responds to everyday commands" and can "explain its approach while performing an action". The page does not mention audio or the Live API. Google is "working with 100+ trusted testers" and runs a waitlist (page undated; family launched 2026-07-30). — [DeepMind Gemini Robotics page](https://deepmind.google/models/gemini-robotics/)
- Gemini Robotics On-Device 2 (model card, July 2026): inputs are text instructions, images and proprioception; output is "Robot actions as numerical values". It is "based on our on-device Gemma models" and Gemini Robotics 1.5 technology, and is "currently available to a select group of trusted testers." The safety section recommends "interfacing VLAs with Embodied Reasoning models for high-level semantic safety." — [On-Device 2 model card](https://deepmind.google/models/model-cards/gemini-robotics-on-device-2/)
- Secondary reporting dated 2026-07-30/31: Gemini Robotics 2 (VLA) is in private preview, ER 2 is in the Gemini API and AI Studio, and On-Device 2 is with trusted partners. On-Device 2 adapts with fewer than 200 examples. — [The Decoder](https://the-decoder.com/google-deepmind-unveils-gemini-robotics-2-to-power-robots-of-all-shapes-from-tabletop-arms-to-humanoids/)

### Inferences
- A single-model "vertically integrated" brain is possible with **ER 2 streaming** as the one Live session. It hears the user, sees at ≤1 fps, reasons spatially, and calls robot tools. The robot would then speak through an external TTS tool (Gemini TTS or Cloud TTS). That costs Reachy native-audio prosody, turn-taking, and proactive audio, all of which are Live audio-model features. ER 2 streaming also has no affective features, and 3.8 Live no longer has affective dialogue either, so the local `detect_emotion` tool remains the emotion path in both designs.
- For a robot whose main job is *conversation*, the Live audio model is still required for natural voice. ER 2 is best placed as a perception and planning tool or sub-agent rather than the voice front end. This matches the current app.
- No VLA is publicly callable for an SO-101 or a Reachy Mini. Gemini Robotics 2 is private preview and On-Device 2 is trusted-tester only. Today the "executor" layer for this project must be the developer's own motion code: taught poses, IK, or a LeRobot policy.

### Gaps
- I found no official statement on whether the Gemini Robotics 2 VLA accepts audio. The DeepMind page and secondary sources mention only "vision and language". No Gemini Robotics 2 model card was reachable: `deepmind.google/models/model-cards/gemini-robotics-2/` returned 404 on 2026-10-15.
- The Live capabilities page says the context window is "128k tokens for native audio output models / 32k tokens for other Live API models". It is unclear whether ER 2 streaming (text-out Live) is capped at 32k inside a Live session or gets its listed 131,072. Unverified.

## 2. Does Gemini Robotics-ER support function calling or tool use, including calling a VLA as a tool and calling user tools like an emotion detector? What are its latency and its "thinking budget" settings?

### Takeaway
Yes. Function calling is supported on both ER 2 endpoints. Google explicitly frames ER as an agent that calls "your robot functions", VLAs, navigation APIs, Google Search and arbitrary user-defined functions. Google's own samples include non-robot user tools such as `get_calendar` and a `run_instruction` tool that hands a natural-language step to a VLA, so an emotion detector is just another declared function. The standard ER 2 also has code execution; streaming does not. Thinking is controlled by `thinking_level`. Google recommends "medium" as the latency/quality balance, its orchestration example uses "low", and its Live sample defaults ER 2 streaming to "low". ER 1.5's numeric "thinking budget" has been replaced by levels in the public API. Google publishes no end-to-end latency numbers for ER 2, only "sub-second" goals for moment-finding and a relative "4x" speed claim.

### Cited Findings
- ER 2 "specializes in embodied reasoning capabilities, such as agentic orchestration of robots (e.g. using VLAs)…". "Gemini Robotics ER is also agentic: it breaks complex tasks into sub-tasks and executes them by calling your robot functions or running generated code." Pointing output "can pass… directly to a robotics API or a VLA model to generate robot actions." (2026-10-06) — [Robotics overview](https://ai.google.dev/gemini-api/docs/robotics-overview)
- Function calling is "Supported" for `gemini-robotics-er-2-preview`, `-streaming-preview` and ER 1.6. Code execution and Search are supported on standard ER 2; streaming has Search but no code execution. (2026-10-08) — [ER 2 model page](https://ai.google.dev/gemini-api/docs/models/gemini-robotics-er-2-preview)
- The Task orchestration example (standard ER 2, Interactions API) declares `move(x,y,high)` and `setGripperState(opened)`. It runs an agent loop that returns `function_result` with `previous_interaction_id` until the model stops calling tools (`max_steps = 15` safety cap), using `generation_config={"thinking_level": "low"}`. (2026-10-01) — [Task orchestration](https://ai.google.dev/gemini-api/docs/robotics-orchestration)
- ER 2 launch post (2026-07-30): ER 2 "hands motor execution to a lower-level vision-language-action (VLA) model". Developers declare low-level control interfaces "such as VLA models or navigation APIs" as tools. It natively calls Google Search or user-defined functions. It reports better orchestration than ER 1.6 with a real VLA, a simulated VLA and human teleoperation (chart only). — [Google blog: ER 2](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)
- ER 1.5 launch (2025-09-25): the model "can call a vision-language-action model (VLA) or any other third-party user-defined functions to execute the task." — [Google Developers Blog: ER 1.5](https://developers.googleblog.com/building-the-next-generation-of-physical-agents-with-gemini-robotics-er-15/)
- Google's Live robotics sample (commit 2026-07-29) declares robot tools (`navigate`, `pick`, `place`, `stand`, `stow`, `move_absolute`, `move_relative`, `stop`) alongside **non-robot user tools** such as `get_calendar` ("Retrieve upcoming events from the shared family calendar") and `send_message` (TTS). — [robotics-samples `agent/tool/tools.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/tool/tools.py)
- The same repo's ER 2 developer-API script says the model streams back "robot action tool calls (e.g., `run_instruction(instruction='...')`)". This is a natural-language handoff to a lower-level policy. — [robotics-samples `er2_developer_api_example.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/scripts/er2_developer_api_example.py)
- Thinking settings: "For thinking level use medium for a good balance between latency and performance." "Complex queries, high-resolution inputs or high thinking levels can lead to increased processing times." The page's examples use `"thinking_level": "high"` and mention cost from "high `thinking_budget`". (2026-10-06) — [Robotics overview](https://ai.google.dev/gemini-api/docs/robotics-overview)
- Google's Live sample registers `gemini-robotics-er-2-streaming-preview` (and `gemini-3.1-flash-live-preview`) with `thinking_level="low"`. The allowed values are `("none","minimal","low","medium","high")`. (2026-07-29) — [robotics-samples `session_config.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/session_config.py)
- A gRPC "Robotics Developer API" (`roboticsdeveloper.googleapis.com`) appears in the sample, with internal model names such as `robotics_er_live_text_only_2p0_no_safety_classifiers` and an "effort_level: Silent thinking effort budget (0.0 to 1.0)". This endpoint is not documented on ai.google.dev. **Unverified for public use**; it appears to be a partner or trusted-tester path. — [robotics-samples `er2_developer_api_example.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/scripts/er2_developer_api_example.py)
- ER 1.5 (2025-09-25) introduced a "flexible thinking budget": "You now have direct control over the latency vs. accuracy trade-off." It suggests quick responses for "detect or point" tasks and longer thinking for multi-step planning. — [Google Developers Blog: ER 1.5](https://developers.googleblog.com/building-the-next-generation-of-physical-agents-with-gemini-robotics-er-15/)
- Latency claims for ER 2 (2026-07-30): moment-finding needs "sub-second latency" to operate robots safely; ER 2 achieves "4x the execution speed" at "a fraction of the compute cost" versus much larger models (baseline unspecified). Moment-finding accuracy is 91.3%, mean absolute error 0.96 s; progress classification is 57.4% across five bands. — [Google blog: ER 2](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/); same figures in [Technobezz](https://www.technobezz.com/news/google-deepmind-launches-gemini-robotics-er-2-for-embodied-robot-reasoning)
- Neither the ER 2 docs page nor the model card gives numeric request latency (ms/s) or thinking-level timing tables. (2026-10-06/08) — [Robotics overview](https://ai.google.dev/gemini-api/docs/robotics-overview), [ER 2 model card](https://deepmind.google/models/model-cards/gemini-robotics-er-2/)

### Inferences
- `detect_emotion` can be declared to ER 2 exactly like `get_calendar` in Google's sample. In an ER-centric design ER would call it. In the current Live-centric design it is simpler to keep it as a Live tool, because emotion matters for *what to say*, not for spatial planning.
- The developer's measured ~10-15 s ER room search is consistent with Google's warning that video inputs and higher thinking levels raise latency. Lowering `thinking_level` to low or medium, sending fewer or lower-resolution frames, and splitting "search" into fast single-frame pointing calls should reduce it. This is an inference; no official numbers exist.
- `run_instruction(instruction)` is the concrete form of the "ER → VLA" interface. If the developer later builds an SO-101 policy (LeRobot ACT or SmolVLA, or the taught poses), exposing it as `run_instruction` or `move_arm(pose)` reproduces Google's layering without needing the restricted Gemini VLA.

### Gaps
- No official numeric latency for ER 2 requests (time to first token, or time per pointing call) at any thinking level.
- It is undocumented whether `thinking_level: "none"` or `"minimal"` is accepted by ER 2 on the public API. Google's sample lists them generically for Gemini, not per model.

## 3. What reference architectures or official examples combine the Live API with Robotics-ER or the VLA?

### Takeaway
Google's published composition is **two-layer: ER as orchestrator, a VLA or robot API as executor**. This is the Gemini Robotics 1.5 "agentic framework" (2025-09) carried into ER 2 (2026-07). The official Live API example is a **single-session** design in which *one* model, either `gemini-3.1-flash-live-preview` (native audio) or `gemini-robotics-er-2-streaming-preview` (text plus TTS tool), is both the conversational and the orchestration brain. It calls robot REST APIs, a TTS tool, peer robots and user tools, with a heartbeat for proactive monitoring. I found **no official example that chains a Live voice model to a separate ER model to a VLA** (the three-layer design the developer is considering). Google does not document that combination, though nothing forbids it.

### Cited Findings
- Gemini Robotics 1.5 framework (2025-09-25): ER 1.5 is "a high-level brain" that "orchestrates a robot's activities". It plans, estimates progress, and calls tools such as Google Search or user functions, then passes "natural language instructions for each step" to the VLA (Gemini Robotics 1.5), which "thinks before acting". — [DeepMind blog: Gemini Robotics 1.5](https://deepmind.google/discover/blog/gemini-robotics-15-brings-ai-agents-into-the-physical-world/)
- Gemini Robotics 2 family (2026-07-30): the VLA and ER models "work together… Each has a specialist role, but they operate as one powerful and versatile system." No mechanism is described on the page. — [DeepMind Gemini Robotics page](https://deepmind.google/models/gemini-robotics/)
- ER 2 Live integration (2026-07-30): ER 2 "integrates with the Gemini Live API" through a bidirectional streaming endpoint for latency-sensitive tasks, aiming to avoid "stop-and-think" pauses and letting the robot think about what comes next while still acting. Demo: ER 2 orchestrates Boston Dynamics Spot navigation and arm APIs to fetch a popcorn snack on a natural-language command; code is on GitHub. — [Google blog: ER 2](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/gemini-robotics-er-2/)
- The official streaming guide's three steps (2026-09-11): "Declare robot capabilities as tools… Physical actions must use `"behavior": "BLOCKING"` so the model waits for the robot to finish before choosing the next step"; "Stream multimodal input into a persistent session"; "Handle tool calls in a receive loop." Plus: "Note: Only blocking function calls are supported when using the Live API for robotics." — [Robotics with streaming](https://ai.google.dev/gemini-api/docs/robotics-streaming)
- Proactive pattern, the "heartbeat" (2026-09-11): "video frames alone do not trigger a new reasoning turn". Send the latest frame plus a `[HEARTBEAT]` text prompt at about 1 Hz, but only after the previous turn completes, because "Sending a new prompt while the model is generating acts as an interruption (barge-in), which cancels in-flight reasoning and tool calls… you may trap the model in a cancellation loop." — [Robotics with streaming](https://ai.google.dev/gemini-api/docs/robotics-streaming)
- Official repo: `google-gemini/robotics-samples/live-api` (single commit "Gemini Robotics ER - Live API Examples", 2026-07-29). The README describes "connecting Gemini Robotics ER with physical robot embodiments using Live API for task orchestration, voice interactions". Embodiments: Spot, "Tinybot (a custom stationary robot hardware)", and human operators. Agent server: FastAPI plus WebSockets plus `google-genai`. — [robotics-samples live-api README](https://github.com/google-gemini/robotics-samples/tree/main/live-api)
- The sample agent's `--model` default is `gemini-3.1-flash-live-preview`, with flags `--use_tts/--no_tts` (default disabled), `--heartbeat_enabled` (default True), `--media_resolution` (default `low`) and `--agent_peers` for multi-robot. — [robotics-samples agent README](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/README.md)
- Tool behaviors in Google's sample: physical moves (`navigate`, `pick`, `place`, `stand`, `sit`, `stow`, `move_absolute`, `move_relative`, `stop`) and also queries (`get_calendar`, `get_battery`, `get_waypoints`, `health_check`) are `BLOCKING`. `send_message` (TTS), `make_gesture`, `open_gripper`, `close_gripper` and `clear_overlay` are `NON_BLOCKING`. — [robotics-samples `tools.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/tool/tools.py)
- The sample's tool handler pauses the heartbeat while any BLOCKING tool runs ("skips sending prompts to avoid re-triggering the model before the tool result is in context"). It sends a fresh camera frame before returning a BLOCKING result: "A blocking FunctionResponse resumes model generation. Send the latest visual context first instead of creating a competing heartbeat turn." — [robotics-samples `tool_call_handler.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/core/tool_call_handler.py)
- The sample runs TTS "in a non-blocking background task". A new utterance cancels in-flight TTS (a `tts_preempt` interruption), "eliminating the delay between speech announcement and action execution." Its default voice is Cloud TTS `en-US-Chirp3-HD-Puck`. — [robotics-samples `decision_making.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/core/decision_making.py), [`tts_client.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/model/tts_client.py)
- The robotics docs point to the general cookbook plus the `robotics-samples` "Getting Started/gemini_robotics_er.ipynb" notebook for non-streaming ER. (2026-10-01) — [Task orchestration](https://ai.google.dev/gemini-api/docs/robotics-orchestration), [notebook](https://github.com/google-gemini/robotics-samples/blob/main/Getting%20Started/gemini_robotics_er.ipynb)
- Secondary (Wikipedia, undated revision): ER 2 added multi-robot collaboration and "lower-latency orchestration via the Gemini Live API". This is consistent with the primary sources. — [Wikipedia: Gemini Robotics](https://en.wikipedia.org/wiki/Gemini_Robotics)

### Inferences
- Google offers **two blessed shapes**. (A) **One Live session as the whole brain**: a voice model with tools, or ER 2 streaming with a TTS tool. (B) **ER orchestrator plus VLA executor** over the request/response or streaming APIs. The developer's current app (3.8 Live, calling ER 2 as a tool, calling local tools) is a **third, unofficial shape**: "voice front end delegates spatial reasoning to ER". It is coherent, but it is the developer's own composition.
- The closest official analogue to the developer's goal is Google's sample run with `--model gemini-robotics-er-2-streaming-preview --use_tts`. That is ER as the single brain, with speech as a tool. Swapping in `gemini-3.1-flash-live-preview` gives the voice-model-as-brain variant. Google ships both in one codebase, which suggests it sees them as alternatives rather than layers.
- A sensible "vertically integrated" design for Reachy plus SO-101, inferred from these sources: Layer 1, **3.8 Live** (voice, emotion tool, persona). Layer 2, **ER 2** called as a tool for perception and planning; it could itself loop over `move_arm` and `look_at` tools via the Interactions API. Layer 3, the **executor**, meaning the developer's arm and head motion code (the stand-in for a VLA). This mirrors GR 1.5's orchestrator/executor split, with a Live voice model on top.

### Gaps
- I found no official Google sample, cookbook notebook or I/O 2026 session that pipes a Live *audio* model into ER into a VLA. A search for I/O 2026 (May 19-20, 2026) robotics or Live sessions returned only aggregator listings, with no official session page or transcript. — [i-programmer I/O 2026 recap](https://i-programmer.info/news/99-professional/18825-google-io-2026-focuses-on-android-and-ai.html) (secondary, no robotics specifics)
- I could not read the Spot "snack fetch" and "Tinybot pan-tilt" demo READMEs in detail. The docs name them, but the repo README only lists `spot/`, `tinybot/` and `agent/` (a hydration-delivery app for Spot).
- It is unclear whether the sample's `NON_BLOCKING` tags are honoured server-side when the model is `gemini-3.1-flash-live-preview` (documented as synchronous-only) or ER 2 streaming (documented as "only blocking"). The client code clearly uses the tag for its own heartbeat gating.

## 4. In the Live API, what exactly do BLOCKING vs NON_BLOCKING and SILENT / WHEN_IDLE / INTERRUPT do? What are the caveats with long-running tools (silence while blocked, barge-in), what does Google recommend for slow tools, and what changed in gemini-3.8-live?

### Takeaway
**BLOCKING**: the model generates nothing until you send the `FunctionResponse`. On `gemini-3.8-live` that means dead air for the whole tool duration. A user barge-in (VAD) during that time cancels the pending call and the server reports the cancelled IDs. **NON_BLOCKING** is the default on 3.8 Live: the conversation continues while the tool runs, and the `scheduling` field you put **in the FunctionResponse** decides delivery. `INTERRUPT` speaks the result now, cutting off current speech. `WHEN_IDLE` speaks it after the current utterance. `SILENT` puts it into context with no speech. For tools that "take several seconds to run", Google's explicit recommendation is **`gemini-3.8-live-extended-thinking`**, which *requires* NON_BLOCKING and speaks conversational fillers automatically. Google's robotics guide, by contrast, insists on **BLOCKING for physical actions** so the planner does not choose a next step before the robot finishes. For a 10-15 s ER room search on `gemini-3.8-live`, the documentation points to **NON_BLOCKING plus WHEN_IDLE plus a prompt rule** (or a move to the extended-thinking model). BLOCKING is documented to give 10-15 s of silence that any noise can cancel.

### Cited Findings
**Definitions (Live tool-use guide, 2026-09-15)**
- "Function calling executes sequentially by default, meaning execution pauses until the results of each function call are available… you won't be able to continue interacting with the model while the functions are being run." "The model will not start responding until you've sent the tool response." This is the BLOCKING behaviour. *Note: this page's "by default" wording and its support table, which lists only 3.1 Flash Live and 2.5 Flash Live, were not updated for 3.8 (see the conflict below).* — [Live API tool use](https://ai.google.dev/gemini-api/docs/live-tools)
- "NON-BLOCKING ensures the function runs asynchronously while you can continue interacting with the model." Behavior is set per function declaration (`"behavior": "NON_BLOCKING"`); undeclared functions "will still pause all interactions". — [Live API tool use](https://ai.google.dev/gemini-api/docs/live-tools)
- Scheduling is set in the FunctionResponse: "Interrupt what it's doing and tell you about the response it got right away (`scheduling="INTERRUPT"`), Wait until it's finished with what it's currently doing (`scheduling="WHEN_IDLE"`), Or do nothing and use that knowledge later on in the discussion (`scheduling="SILENT"`)". In the JS SDK this is `FunctionResponseScheduling.INTERRUPT`. — [Live API tool use](https://ai.google.dev/gemini-api/docs/live-tools)
- "Unlike the generateContent API, the Live API doesn't support automatic tool response handling". The client must call `session.send_tool_response`. — [Live API tool use](https://ai.google.dev/gemini-api/docs/live-tools)

**What changed in 3.8**
- "Asynchronous function calling: Async execution (`behavior: NON_BLOCKING`) is now the default function calling mode. You can still use synchronous blocking mode for backwards compatibility by setting `behavior: BLOCKING` on your tool declarations. Function scheduling (`SILENT`, `WHEN_IDLE`, `INTERRUPTED`) is supported." (2026-09-15) — [Gemini 3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)
- Model comparison (2026-09-18). 3.8 Live: async "Supported (default)… or… `BLOCKING`. Function scheduling… supported." 3.8 Live Extended Thinking: "Supported (Async only). Only NON_BLOCKING execution is supported. Blocking mode and function scheduling are not supported." 3.1 Flash Live Preview: "Not supported. Function calling is sequential only." — [Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)
- Gemini 2.5 Flash Live Preview supported "synchronous and asynchronous" function calling. 3.1 Flash Live was "synchronous only" ("Asynchronous function calling is not yet supported in Gemini 3.1 Flash Live"). So 3.8 restores async and makes it the default. (2026-09-15) — [Live API tool use](https://ai.google.dev/gemini-api/docs/live-tools)
- `send_client_content` "is supported throughout the entire session lifecycle with explicit roles (`user` or `model`). Setting `turn_complete=true` unconditionally interrupts active model generation. If you send content without `turn_complete`, the server waits for subsequent messages before responding." (2026-09-15) — [Gemini 3.8 Live model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live)
- `thinking_level` is not supported on `gemini-3.8-live` ("Interleaved reasoning with fixed latency profile"). It is configurable (low, medium or high, with no minimal) on `gemini-3.8-live-extended-thinking`. (2026-09-15) — [Live API Thinking](https://ai.google.dev/gemini-api/docs/live-api/thinking)

**Silence, barge-in, cancellation**
- The Thinking guide frames the problem (2026-09-15): without background reasoning, "The model must either answer without reasoning or pause silently while waiting for tools to finish." Its comparison table, "Conversational fillers" row: Gemini 3.8 Live "Model waits for tool execution before speaking"; Extended Thinking "Model streams intermediate conversational fillers while processing". — [Live API Thinking](https://ai.google.dev/gemini-api/docs/live-api/thinking)
- Barge-in: "When VAD detects an interruption, the ongoing generation is canceled and discarded. Only the information already sent to the client is retained in the session history… The Gemini server then discards any pending function calls and sends a `BidiGenerateContentServerContent` message with the IDs of the canceled calls." The default end-of-speech silence is about 800 ms; the recommended `silenceDurationMs` is 500-800 ms. (2026-09-18) — [Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)
- Robotics caution (2026-09-11): a new prompt during generation "acts as an interruption (barge-in), which cancels in-flight reasoning and tool calls". Blind-timer heartbeats can cause "a cancellation loop". — [Robotics with streaming](https://ai.google.dev/gemini-api/docs/robotics-streaming)

**Google's recommendation for slow tools**
- "Use `gemini-3.8-live` for… Fast tool execution: Workflows where external tools return within milliseconds (such as reading sensor values or controlling smart devices)." "Use `gemini-3.8-live-extended-thinking` when your agent must evaluate complex data, plan multiple steps, or handle tools that take several seconds to run", including "Voice experiences where long-running functions would otherwise create awkward silence for the listener." (2026-09-15) — [Live API Thinking](https://ai.google.dev/gemini-api/docs/live-api/thinking)
- Extended Thinking requirements: "Set `"behavior": "NON_BLOCKING"` on all function declarations… Synchronous blocking tools return an error." Clients must "Track `interaction_status` instead of `turnComplete`" (`IN_PROGRESS` vs `IDLE`), because a filler such as "Checking flights to Seattle..." arrives with `turnComplete: true` while still `IN_PROGRESS`. (2026-09-15) — [Live API Thinking](https://ai.google.dev/gemini-api/docs/live-api/thinking)
- Robotics guidance (ER 2 streaming, 2026-09-11): "Physical actions must use `"behavior": "BLOCKING"` so the model waits for the robot to finish before choosing the next step." "Only blocking function calls are supported when using the Live API for robotics." — [Robotics with streaming](https://ai.google.dev/gemini-api/docs/robotics-streaming)
- Prompting guidance (2026-09-15): "The model performs best on tasks with single function calls." "Be sure to tell Gemini under what conditions a tool call should be invoked." — [Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)

**Documentation conflicts to flag**
- The default behavior conflicts. The 3.8 model page and capabilities table say NON_BLOCKING is the default ([model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-live), [capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)). The tool-use guide, updated the same day (2026-09-15), still says "Function calling executes sequentially by default" and its code comment says an undeclared function "will still pause all interactions" ([live-tools](https://ai.google.dev/gemini-api/docs/live-tools)). The likely reading is that the guide is stale for 3.8, but this is **unverified**. Set `behavior` explicitly on every declaration.
- The scheduling enum spelling conflicts. The 3.8 model page and capabilities table write `INTERRUPTED`; the tool guide and SDK samples use `INTERRUPT` / `FunctionResponseScheduling.INTERRUPT`. Use the SDK enum rather than a raw string. Which raw string the 3.8 server accepts is **unverified**.

### Inferences
- **Recommendation for the ~10-15 s ER room search on `gemini-3.8-live`:** declare it `NON_BLOCKING` (explicitly) and return the result with `scheduling: WHEN_IDLE`. Add a system-prompt rule along these lines: "When you call `search_room`, say briefly that you're looking. Never state where an object is until the search result arrives. If asked meanwhile, say you're still looking." Reasons:
  1. With BLOCKING, the documented behaviour is total silence until the response ("Model waits for tool execution before speaking"). That means 10-15 s of dead air on a social robot.
  2. Any VAD-detected speech or noise during that window cancels the pending call (IDs reported). The client must then abort the ER request or drop its late result, otherwise it will try to answer a cancelled call ID.
  3. Google itself positions 3.8 Live for millisecond tools and sends multi-second tools to the async-only extended-thinking model.
- **WHEN_IDLE vs INTERRUPT vs SILENT for this robot:**
  - `WHEN_IDLE` for search and planning results the user is waiting for: it avoids cutting Reachy off mid-sentence.
  - `INTERRUPT` only for safety or urgency results, such as "motor fault" or "object found while user is walking away".
  - `SILENT` for context updates the model should use but not announce: periodic `detect_emotion`, arm-move completion acknowledgements. This matches the repo's recent commit "answer move_arm silently".
- **Physical arm moves are different.** If Live itself sequences multi-step arm motion where step N+1 depends on step N finishing, Google's robotics guidance favours BLOCKING. A NON_BLOCKING tool backed by an **app-side motion queue** that serialises moves and reports completion SILENTly (the developer's current approach) achieves the same ordering without muting the voice. A BLOCKING `move_arm` would silence Reachy for the whole move and make it cancellable by noise.
- **Alternative for slow tools:** switch the session to `gemini-3.8-live-extended-thinking`. Fillers are then automatic, but scheduling control is lost (not supported), BLOCKING is impossible (errors), and the client must track `interaction_status`. Background reasoning presumably adds latency and cost per turn; that last point is inference.
- **Late-result injection:** a long ER job could run outside the tool mechanism, returning an immediate "started" response, and later inject its result with `send_client_content` (role `user`, `turn_complete=false` to avoid interrupting). This is allowed "throughout the entire session lifecycle" on 3.8. But `turn_complete=true` "unconditionally interrupts" generation, so it behaves like INTERRUPT. This option is inferred from the docs and untested.
- **Risk with NON_BLOCKING:** the model can talk before the result exists, and may guess an answer or re-call the tool. That is why the prompt rule matters. Google documents no guardrail for this; it is a common failure mode of async tools in general and is **not evidenced in Google docs**.

### Gaps
- There is no official statement on whether user speech is still transcribed and buffered *during* a BLOCKING call (beyond the cancellation of the pending call), or whether proactive audio (always on in 3.8) can speak during a BLOCKING wait.
- There is no official guidance on tool timeouts or a maximum tool duration in the Live API, or on what happens if a NON_BLOCKING response arrives after its call was cancelled by barge-in.
- I found no official 3.8 Live latency figures (time to first audio).

## 5. How do latency, cost and context management differ between a Live-centric design and an ER-orchestrator-centric design?

### Takeaway
**Live-centric** (3.8 Live as brain, ER 2 called as a request/response tool, local tools): the fastest and most natural voice. Spatial work costs a separate ER request (10-15 s here) and a second, stateless context, because ER does not see the conversation unless you pass it. **ER-orchestrator-centric** (ER 2 streaming as the single Live brain with a TTS tool): one context with spatial reasoning always in the loop and cheaper token rates through 2026. But voice is text-to-TTS, function calls are "only blocking" for robotics, there is no async scheduling, and proactive behaviour needs a heartbeat. Both inherit Live session limits: 2 min audio+video without compression, about 10 min per connection, resumption tokens valid for 2 h. Both inherit compounding per-turn billing, so context compression is mandatory for an always-on robot.

### Cited Findings
**Pricing (paid tier, per 1M tokens; page updated 2026-10-15)** — [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing)
- Gemini 3.8 Live, 3.8 Live Extended Thinking and 3.1 Flash Live Preview share one table. Input: text $0.75, audio $3.00 (or $0.005/min), image/video $1.00 (or $0.002/min). Output: text $4.50, audio $12.00 (or $0.018/min). A free tier is available.
- ER 2 Preview and ER 2 Streaming Preview: input (text, image, video and audio at the same rate) $1.00 through 2026-12-31, rising to $2.00 from 2027-01-01. Output $5.00, rising to $10.00 from 2027-01-01. A free tier is available.
- Third-party aggregators disagree on the ER 2 price ($2/$10 vs $1/$5). The difference is explained by Google's promotional rate running to the end of 2026. — [cloudprice.net](https://cloudprice.net/models/gemini/gemini-robotics-er-2-preview)

**Live billing and context mechanics (2026-09-15)** — [Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)
- "The API charges you per turn for all tokens present in the session context window… Past tokens are re-processed and accounted for in each new turn." It "retains conversational history as raw audio tokens", and audio accumulates at "approximately 25 tokens per second". Transcription is charged extra at the text-output rate.
- The page suggests compression, for example a trigger at 25,000 tokens and a sliding window of 8,000. "Proactive audio is permanently enabled in gemini-3.8-live and gemini-3.8-live-extended-thinking": input is charged "the entire time the Live API is listening."
- Audio-only sessions are limited to 15 minutes and audio+video sessions to 2 minutes without compression. The connection lifetime is "around 10 minutes". A `GoAway` message warns before disconnect. "Resumption tokens are valid for 2 hr." (2026-09-15) — [Live session management](https://ai.google.dev/gemini-api/docs/live-session)
- Context window: "128k tokens for native audio output models / 32k tokens for other Live API models." (2026-09-18) — [Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)
- Client tips: send 20-100 ms audio chunks and resample to 16 kHz. (2026-09-15) — [Live API best practices](https://ai.google.dev/gemini-api/docs/live-api/best-practices)

**ER-centric specifics**
- ER 2 streaming needs a heartbeat (frame plus text at about 1 Hz) for proactive behaviour, because "video frames alone do not trigger a new reasoning turn". Each heartbeat is a model turn. (2026-09-11) — [Robotics with streaming](https://ai.google.dev/gemini-api/docs/robotics-streaming)
- Speech must go through an external TTS (Gemini TTS or Cloud TTS; Google's sample uses Chirp 3 HD). That is a separate service, with its own latency and cost. — [Robotics with streaming](https://ai.google.dev/gemini-api/docs/robotics-streaming), [robotics-samples `tts_client.py`](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/model/tts_client.py)
- ER 2 streaming lacks caching, code execution and structured outputs. Standard ER 2 has them, plus Batch API, but no Live. (2026-10-08) — [ER 2 model page](https://ai.google.dev/gemini-api/docs/models/gemini-robotics-er-2-preview)
- Latency levers per Google: thinking level (medium for balance), input resolution, and query complexity. The sample defaults `media_resolution` to `low` and `thinking_level` to `low`. — [Robotics overview](https://ai.google.dev/gemini-api/docs/robotics-overview), [robotics-samples agent README](https://github.com/google-gemini/robotics-samples/blob/main/live-api/agent/README.md)
- 3.8 Live has a "fixed latency profile" with no thinking knob. Extended Thinking trades latency for background planning. (2026-09-15) — [Live API Thinking](https://ai.google.dev/gemini-api/docs/live-api/thinking)

### Inferences
**Comparison of the three designs (inferred from the sources above):**

| Dimension | A. Live-centric (current) | B. ER-streaming-centric (Google sample with ER) | C. Three-layer Live → ER → executor |
|---|---|---|---|
| Voice quality and latency | Best: native audio, server VAD turn-taking, proactive audio | Worse: text, then TTS hop; TTS barge-in handled by the app | Same as A |
| Spatial reasoning in the loop | Only when Live calls the ER tool (adds 1 HTTP round trip; ~10-15 s measured by the developer for search) | Always; ER sees every frame | Same as A, but ER can run its own multi-step tool loop |
| Tool semantics | NON_BLOCKING plus scheduling available | "Only blocking" for robotics; no scheduling | Live: async; ER inner loop: request/response |
| Contexts | Two: Live session plus a stateless ER call per tool; pass the needed conversation into each ER prompt | One shared context | Two or three; needs explicit state handoff |
| Cost drivers | Audio in $3/M every turn (compounding), audio out $12/M, plus ER $1/$5 per call | $1/M for all input including audio, $5/M out (2026 rate), plus TTS, plus heartbeat turns | A plus ER inner-loop tokens |
| Video limit | 1 fps; 2 min A+V without compression | 1 fps JPEG; same Live limits | Live 1 fps; ER call can take higher-resolution single images |

- On raw token price, ER 2 streaming is cheaper per input token than 3.8 Live audio input ($1 vs $3 per 1M, through 2026; $2 vs $3 from 2027). But design B adds TTS costs and about 1 Hz heartbeat turns, each re-billing the accumulated context. An always-watching ER loop could cost more overall than a Live session that calls ER only on demand. This is an estimate; no measured figures exist.
- **Context management:** in design A, keep the Live session lean. Use context compression, send video only when needed (3.8's default now includes all video in turns), and summarise ER results back as short text. Design A's main weakness is that ER lacks conversational context. Mitigate it by passing a compact task description and the latest frames in each ER call, or by keeping a long-lived ER Interactions thread with `previous_interaction_id`.
- **Fit with the developer's goals and the memory note "keep Gemini app, migrate to 3.8 Live, run emotion locally":** design A or C best preserves a natural talking robot. Design B makes sense only if spatial autonomy (continuous monitoring, multi-step manipulation) becomes more important than voice quality.

### Gaps
- No official numeric latency for 3.8 Live (time to first audio), ER 2 streaming (time to first token or time to tool call), or Gemini TTS, so the latency comparison is qualitative.
- It is unclear whether the 2-minute audio+video session limit applies identically to ER 2 streaming (the limits are stated for "Live API" generally).
- There is no official cost calculator for heartbeat-driven ER streaming sessions, and no guidance on recommended compression settings for robotics sessions.
